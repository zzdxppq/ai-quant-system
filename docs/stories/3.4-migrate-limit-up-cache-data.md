## Epic Context
**Epic**: 3 - 数据库迁移 JSON→PostgreSQL 支持并发读写
将系统数据存储从 JSON 文件迁移到 PostgreSQL 数据库，支持并发读写访问。
涉及 decision_records 和 limit_up_cache 两个核心数据表的迁移，
并改造业务代码使用统一的 DB 接口层，消除文件锁竞争，提升多进程并发性能。
**Story Deliverables**: limit_up_cache JSON 数据迁移到 PostgreSQL，数据完整性验证

## Data Structure Analysis

### Source: JSON File
```json
{
  "20260519": [
    { "code": "600021", "name": "上海电力", "change_pct": 10.018 },
    ...
  ]
}
```

**字段说明**:
| JSON 字段 | 类型 | 说明 |
|-----------|------|------|
| (date key) | string (YYYYMMDD) | 交易日期 |
| code | string | 股票代码 |
| name | string | 股票名称 |
| change_pct | float | 涨幅百分比 |

### Target: DB Table `limit_up_cache`
| DB 字段 | 类型 | 说明 |
|---------|------|------|
| date | DATE | 交易日期 |
| stock_code | VARCHAR(10) | 股票代码 |
| continuous_limit_days | INTEGER | 连板天数（**JSON 无此字段**） |
| first_limit_time | TIME | 首次涨停时间（**JSON 无此字段**） |
| last_updated | TIMESTAMP | 最后更新时间（自动） |

### 字段映射规则
| JSON → DB | 映射策略 |
|-----------|---------|
| date key → date | 转换格式：YYYYMMDD → YYYY-MM-DD |
| code → stock_code | 直接映射 |
| name → (无对应列) | **不迁移**，JSON 快照属性，DB 无此列 |
| change_pct → (无对应列) | **不迁移**，同 name |
| continuous_limit_days | 默认值 **1**（视为首次涨停，真实连板数需 Story 5.x 回补计算） |
| first_limit_time | 默认值 **'09:25:00'**（标准竞价时间） |

> ⚠️ **重要约束**: `continuous_limit_days` 和 `first_limit_time` 在 JSON 中无源数据。
> 迁移后需在 Story 5.x 中通过历史 K 线数据回填真实的连板天数。
> 本次迁移接受默认值 1，不因此阻塞 AC4 完整性校验。

## Acceptance Criteria

### AC1: 读取现有 JSON 文件

**Scenario**
```gherkin
GIVEN 系统已有 limit_up_cache.json 文件
WHEN 执行数据迁移
THEN 读取 JSON 文件内容
  - 文件路径: data/limit_up_cache.json
  - 解析 JSON 字典格式（key=YYYYMMDD，value=股票列表）
  - 处理大文件（分块读取）
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-1.1 | 文件不存在时跳过迁移并记录警告 |
| BR-1.2 | JSON 解析错误时记录错误并跳过该文件 |
| BR-1.3 | 空对象 {} 视为成功（无需迁移） |
| BR-1.4 | 每条记录必须包含 code 字段，无 code 者跳过并记录 |

**Error Handling**
| Scenario | Code | Message | Action |
|----------|------|---------|--------|
| 文件不存在 | FileNotFound | limit_up_cache.json not found | 记录警告，跳过迁移 |
| JSON 解析错误 | JSONDecodeError | invalid JSON format | 记录错误，中断迁移 |
| 记录缺少 code | MissingField | record missing 'code' field | 跳过该记录，继续 |

---

### AC2: 批量导入 PostgreSQL

**Scenario**
```gherkin
GIVEN JSON 文件解析成功
WHEN 执行批量导入
THEN 将数据导入 PostgreSQL
  - 使用 upsert 逻辑（已存在则更新）
  - 每批 1000 条记录
  - 事务包装保证原子性
  - continuous_limit_days 默认 1，first_limit_time 默认 '09:25:00'
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-2.1 | 使用 ON CONFLICT (date, stock_code) DO UPDATE 实现 upsert |
| BR-2.2 | 批量插入使用 executemany |
| BR-2.3 | 整个 JSON 文件作为单一事务 |
| BR-2.4 | JSON 中无 continuous_limit_days → 置为默认值 1 |
| BR-2.5 | JSON 中无 first_limit_time → 置为默认值 '09:25:00' |
| BR-2.6 | date 格式统一转换为 YYYY-MM-DD（JSON 为 YYYYMMDD） |

**Error Handling**
| Scenario | Code | Message | Action |
|----------|------|---------|--------|
| 部分数据错误 | PartialFailure | some records failed | 记录失败记录，继续处理 |
| 事务失败 | TransactionError | transaction rolled back | 回滚并报告错误 |

### AC4: 数据完整性校验

**Scenario**
```gherkin
GIVEN 数据导入完成
WHEN 执行完整性校验
THEN 验证数据迁移正确性
  - JSON 股票记录总数 = PostgreSQL 记录数（含 upsert 更新的记录）
  - 抽样验证字段完整性（stock_code, date 格式）
  - 记录迁移报告
```

**Business Rules**
| ID | Rule |
|----|------|
| BR-4.1 | JSON 总股票条目数（所有日期累加）必须等于 PG 记录数 |
| BR-4.2 | 抽样比例: 随机抽取 10 条验证 stock_code 非空、date 格式正确 |
| BR-4.3 | 生成迁移报告包含: 总记录数、导入成功数、失败数、跳过的记录数 |
| BR-4.4 | continuous_limit_days=1 和 first_limit_time='09:25:00' 不参与校验不匹配判定 |

> ⚠️ 注意: 因 JSON 缺少 continuous_limit_days 和 first_limit_time 的源数据，
> 这两个字段不参与 AC4 的抽样比对。

**Error Handling**
| Scenario | Code | Message | Action |
|----------|------|---------|--------|
| 记录数不匹配 | CountMismatch | JSON count != PG count | 报告差异，不删除备份 |
| 抽样验证失败 | ValidationFailed | field values mismatch | 报告差异，不删除备份 |

### Implementation Summary
Created migration script `scripts/migrate_limit_up_cache.py`:
- Reads JSON with date-keyed structure `{date_YYYYMMDD: [stocks]}`
- Transforms records with defaults: continuous_limit_days=1, first_limit_time='09:25:00'
- Batch imports using ON CONFLICT DO UPDATE upsert (1000/batch)
- Creates JSON backup on success (`.bak`)
- Verifies integrity with count match + random sampling (10 records)
- Generates migration report to `data/migration_report_limit_up_cache.json`

Key decisions:
- Uses upsert (not TRUNCATE) to preserve pre-existing data
- Default continuous_limit_days=1, first_limit_time='09:25:00' for missing fields
- Date format conversion YYYYMMDD → YYYY-MM-DD
